USER-RATING-MICROSERVICES PROJECT DETAILS

PROJECT ARCHITECTURE
- client-server architecture 
- Client's any request -> api-gateway -> analyzes request URL & decides where(service) request should be 
routed -> targeted service's controller & process request with sending response
- Okta Auth for securing api requests and its authentication-authorization part at api-gateway
- service-registry -> saves all details of all services with name, url, port number, status
- config-server -> Used github repository, to save common configurations -> 
fetched by services, while running
- each service has individual DBs

IMPLEMENTING CIRCUIT BREAKER PATTERN
- In USER-SERVICE, circuit breaker is added
- Add dependancy actuator, aop and resilience4j-spring-boot3 - to enable annotations and 
classes
- In target controller's method, use @CircuitBreaker & maintain fallback method
@CircuitBreaker(name = "userServiceCircuitBreaker", fallbackMethod = "fetchUserByIdFallback")
- Fallback method should have same return type and parameters as the original method along 
with an additional parameter of type Throwable to capture the exception details
- configuration in yml for circuit breaker:
resilience4j:
  circuitbreaker:
    instances:
      userServiceCircuitBreaker:
        registerHealthIndicator: true
        eventConsumerBufferSize: 10
        minimumNumberOfCalls: 5  
        failureRateThreshold: 50
        waitDurationInOpenState: 6s
        permittedNumberOfCallsInHalfOpenState: 3
        automaticTransitionFromOpenToHalfOpenEnabled: true
        slidingWindowSize: 10
        slidingWindowType: COUNT_BASED
- Flow:
  1. Failure Decision:
  minimumNumberOfCalls: 5
  failureRateThreshold: 50
  👉 Meaning:
  Wait for at least 5 calls
  If 50% fail, then → OPEN circuit
  📌 Easy memory:
  “5 calls → 50% fail → open”

  2. Sliding Window:
  slidingWindowSize: 10
  slidingWindowType: COUNT_BASED
  👉 Meaning:
  Check last 10 requests
  Based on count (not time)
  📌 Memory:
  “Check last 10 calls”

  3. Open State Timing:
  waitDurationInOpenState: 6s
  👉 Meaning:
  Stay OPEN for 6 seconds
  No calls allowed during this time
  📌 Memory:
  “Fail → sleep 6 sec”

  4. Half-Open Testing:
  permittedNumberOfCallsInHalfOpenState: 3
  👉 Meaning:
  After 6 sec → allow only 3 test calls
  📌 Memory:
  “After sleep → test 3 calls”

  5. Auto Transition:
  automaticTransitionFromOpenToHalfOpenEnabled: true
  👉 Meaning:
  Automatically move from OPEN → HALF-OPEN
  (no manual trigger needed)

  6. Monitoring / Metric:
  registerHealthIndicator: true
  eventConsumerBufferSize: 10
  👉 Meaning:
  Expose health info (for Actuator)
  Store last 10 events (for debugging)

RETRY MECHANISM USING resilience4j
Request comes
→ Retry tries 3 times
→ Failures counted in Circuit Breaker
→ If threshold crossed → Circuit OPEN
→ Fallback executed

Next request:
→ Circuit OPEN
→ No retry
→ Direct fallback

- Use @Retry in controller method, which you are targeting
    @Retry(name = "userServiceRetry", fallbackMethod = "fetchUserByIdFallback")
- Maintain different fallback method of circuitbreaker and retry mechanism
- Fallback is executed ONLY after:
    - Retry is exhausted OR
    - Circuit is OPEN
- Maintain configuration:
    resilience4j:
        retry:
            instances:
                userServiceRetry:
                    maxAttempts: 3  #maximum 3 times (1 original + 2 retries)
                    waitDuration: 2s  #Wait 2 seconds between retries
                    retryExceptions:
                    - java.lang.IllegalStateException  #Retry only for allowed Exceptions
                    ignoreExceptions:
                    - java.lang.NullPointerException  #Don't retry for this Exceptions


RATE LIMITER USING resilience4j
- Helps in security and performance of application
- Security: does not allow spam/bots to call service multiple times unnecessarily, leading
to server down
-Performace: Makes application always available to serve genuine requests from Clients, improved
scalabilty, reliability
- Need, same dependancy as CircuitBreaker - aop and resilience4j-spring-boot3
@RateLimiter(name = "userServiceRateLimiter", fallbackMethod = "rateLimitFetchUserByIdFallback")
- Max 5 calls
- Per 1 minute
- No waiting (fail fast)
- yml configuration for retry mechanism:
    resilience4j:
        rateLimiter:
            instances:
            userServiceRateLimiter:
                limitForPeriod: 5  # Max 5 calls per period
                limitRefreshPeriod: 1m  # in every 1 minute
                timeoutDuration: 0  # No waiting, fail immediately if limit exceeded - (fail fast)
- desired Balanced configuration: 
    limitForPeriod: 10
    limitRefreshPeriod: 1s
    timeoutDuration: 2s


OKTA FOR AUTHENTICATION AND AUTHORIZATION WITH SPRING SECURITY 
- How it works:
    - request made by client to api-gateway -> authenticate user with spring security
    and okta auth -> api-gateway sends response+token (generated by okta) -> any new requests
    made by client to apigateway had token in header -> any service/api-gateway verifies, header
    -> verified - allowed access -> else denied.
- Okta Configuiration:
    Create Okta account (free) -> create application - allow client credentials, maintain correct redirect URIs, cleint secrets and 
    ID is important -> create new users and groups -> assign users to groups and application 
    -> create new scope and claim (claim is part of tokem when created, scope is part of authorization 
    - we created internal scope - for valid internal communication between services)
- Okta to be implemented in api-gateway, as first client requests reaches gateway, then 
targeted services
- Add 2 necessary dependancies, of okta and spring security
- Use @
- Create Configuration file with annotation - @EnableWebFluxSecurity, to create Bean of SecurityWebFilterChain, 
create controller & model for serving request & to give response (with token)
- @EnableWebFluxSecurity - is required because in api-gateway we use webflux dependancy, and to implement
security we need this annotation at configuration file
- 
- So your Gateway is doing TWO roles:
    1. OAuth2 Client → handles login (Okta) (authentication)
    2. Resource Server → validates JWT
    @Bean
    public SecurityWebFilterChain getSecurityWebFilterChain(ServerHttpSecurity http) 
    {
        return http
                .csrf().disable() 
                // Disable CSRF protection (not needed for stateless APIs using JWT)
                .authorizeExchange()
                // Start defining authorization rules for incoming requests
                .pathMatchers("/auth/**").permitAll()
                // Allow all requests to /auth/** without authentication (public endpoints)
                .anyExchange().authenticated()
                // Any other request must be authenticated
                .and()
                .oauth2Login()
                // Enables OAuth2 login (redirects user to Okta login page)
                .and()
                .oauth2Client()
                // Enables OAuth2 client features (used for token exchange & communication with Okta)
                .and()
                .oauth2ResourceServer()
                // Configures this app as a Resource Server
                .jwt()
                // Enables JWT token validation for incoming requests
                .build();
                // Build and return the security filter chain
    }
