IMPLEMENTING CIRCUIT BREAKER PATTERN
- In USER-SERVICE, circuit breaker is added
- Add dependancy actuator, aop and resilience4j-spring-boot3 - to enable annotations and 
classes
- In target controller's method, use @CircuitBreaker & maintain fallback method
@CircuitBreaker(name = "userServiceCircuitBreaker", fallbackMethod = "fetchUserByIdFallback")
- Fallback method should have same return type and parameters as the original method along 
with an additional parameter of type Throwable to capture the exception details
- configuration in yml for circuit breaker:
resilience4j:
  circuitbreaker:
    instances:
      userServiceCircuitBreaker:
        registerHealthIndicator: true
        eventConsumerBufferSize: 10
        minimumNumberOfCalls: 5  
        failureRateThreshold: 50
        waitDurationInOpenState: 6s
        permittedNumberOfCallsInHalfOpenState: 3
        automaticTransitionFromOpenToHalfOpenEnabled: true
        slidingWindowSize: 10
        slidingWindowType: COUNT_BASED
- Flow:
  1. Failure Decision:
  minimumNumberOfCalls: 5
  failureRateThreshold: 50
  👉 Meaning:
  Wait for at least 5 calls
  If 50% fail, then → OPEN circuit
  📌 Easy memory:
  “5 calls → 50% fail → open”

  2. Sliding Window:
  slidingWindowSize: 10
  slidingWindowType: COUNT_BASED
  👉 Meaning:
  Check last 10 requests
  Based on count (not time)
  📌 Memory:
  “Check last 10 calls”

  3. Open State Timing:
  waitDurationInOpenState: 6s
  👉 Meaning:
  Stay OPEN for 6 seconds
  No calls allowed during this time
  📌 Memory:
  “Fail → sleep 6 sec”

  4. Half-Open Testing:
  permittedNumberOfCallsInHalfOpenState: 3
  👉 Meaning:
  After 6 sec → allow only 3 test calls
  📌 Memory:
  “After sleep → test 3 calls”

  5. Auto Transition:
  automaticTransitionFromOpenToHalfOpenEnabled: true
  👉 Meaning:
  Automatically move from OPEN → HALF-OPEN
  (no manual trigger needed)

  6. Monitoring / Metric:
  registerHealthIndicator: true
  eventConsumerBufferSize: 10
  👉 Meaning:
  Expose health info (for Actuator)
  Store last 10 events (for debugging)

RETRY MECHANISM USING resilience4j
Request comes
→ Retry tries 3 times
→ Failures counted in Circuit Breaker
→ If threshold crossed → Circuit OPEN
→ Fallback executed

Next request:
→ Circuit OPEN
→ No retry
→ Direct fallback

- Visual Flow
	Main Method
	   ↓
	Failure
	   ↓
	Retry 1
	   ↓
	Failure
	   ↓
	Retry 2
	   ↓
	Failure
	   ↓
	Retry 3
	   ↓
	Failure
	   ↓
	Fallback Method

- Use @Retry in controller method, which you are targeting
    @Retry(name = "userServiceRetry", fallbackMethod = "fetchUserByIdFallback")
- Maintain different fallback method of circuitbreaker and retry mechanism
- Fallback is executed ONLY after:
    - Retry is exhausted OR
    - Circuit is OPEN
- Maintain configuration:
    resilience4j:
        retry:
            instances:
                userServiceRetry:
                    maxAttempts: 3  #maximum 3 times (1 original + 2 retries)
                    waitDuration: 2s  #Wait 2 seconds between retries
                    retryExceptions:
                    - java.lang.IllegalStateException  #Retry only for allowed Exceptions
                    ignoreExceptions:
                    - java.lang.NullPointerException  #Don't retry for this Exceptions


RATE LIMITER USING resilience4j
- Helps in security and performance of application
- Security: does not allow spam/bots to call service multiple times unnecessarily, leading
to server down
-Performace: Makes application always available to serve genuine requests from Clients, improved
scalabilty, reliability
- Need, same dependancy as CircuitBreaker - aop and resilience4j-spring-boot3
@RateLimiter(name = "userServiceRateLimiter", fallbackMethod = "rateLimitFetchUserByIdFallback")
- Max 5 calls
- Per 1 minute
- No waiting (fail fast)
- yml configuration for retry mechanism:
    resilience4j:
        rateLimiter:
            instances:
            userServiceRateLimiter:
                limitForPeriod: 5  # Max 5 calls per period
                limitRefreshPeriod: 1m  # in every 1 minute
                timeoutDuration: 0  # No waiting, fail immediately if limit exceeded - (fail fast)
- desired Balanced configuration: 
    limitForPeriod: 10
    limitRefreshPeriod: 1s
    timeoutDuration: 2s


OKTA FOR AUTHENTICATION AND AUTHORIZATION WITH SPRING SECURITY 
- How it works:
    - request made by client to api-gateway -> authenticate user with spring security
    and okta auth -> api-gateway sends response+token (generated by okta) -> any new requests
    made by client to apigateway had token in header -> any service/api-gateway verifies, header
    -> verified - allowed access -> else denied.
- Okta Configuiration:
    Create Okta account (free) -> create application - allow client credentials, maintain correct redirect URIs, cleint secrets and 
    ID is important -> create new users and groups -> assign users to groups and application 
    -> create new scope and claim (claim is part of tokem when created, scope is part of authorization 
    - we created internal scope - for valid internal communication between services)
- Okta to be implemented in api-gateway, as first client requests reaches gateway, then 
targeted services
- So your Gateway is doing TWO roles:
    1. OAuth2 Client → handles login (Okta) (authentication)
    2. Resource Server → validates JWT & routes request to service
- Add 2 necessary dependancies, of okta and spring security
- Create Configuration file with annotation - @EnableWebFluxSecurity, to create Bean of SecurityWebFilterChain, 
create controller & model for serving request & to give response (with token)
- @EnableWebFluxSecurity - is required because in api-gateway we use webflux dependancy, and to implement
security we need this annotation at configuration file
- Configuiration file for API-GATEWAY:
    @Bean
    public SecurityWebFilterChain getSecurityWebFilterChain(ServerHttpSecurity http) 
    {
        return http
                .csrf().disable() 
                // Disable CSRF protection (not needed for stateless APIs using JWT)
                .authorizeExchange()
                // Start defining authorization rules for incoming requests
                .pathMatchers("/auth/**").permitAll()
                // Allow all requests to /auth/** without authentication (public endpoints)
                .anyExchange().authenticated()
                // Any other request must be authenticated
                .and()
                .oauth2Login()
                // Enables OAuth2 login (redirects user to Okta login page)
                .and()
                .oauth2Client()
                // Enables OAuth2 client features (used for token exchange & communication with Okta)
                .and()
                .oauth2ResourceServer()
                // Configures this app as a Resource Server
                .jwt()
                // Enables JWT token validation for incoming requests
                .build();
                // Build and return the security filter chain
    }

    @Bean
    public JwtAuthenticationConverter jwtAuthenticationConverter() {

        JwtAuthenticationConverter jwtConverter = new JwtAuthenticationConverter();

        jwtConverter.setJwtGrantedAuthoritiesConverter(jwt -> {

            Collection<GrantedAuthority> authorities = new ArrayList<>();

            // ✅ Add scopes
            JwtGrantedAuthoritiesConverter scopeConverter = new JwtGrantedAuthoritiesConverter();
            authorities.addAll(scopeConverter.convert(jwt));

            // ✅ Add custom claim (myclaim)
            List<String> roles = jwt.getClaimAsStringList("myclaim");
            if (roles != null) {
                roles.forEach(role -> authorities.add(new SimpleGrantedAuthority(role)));
            }
            return authorities;
        });

        return jwtConverter;
    }
- SecurityWebFilterChain bean is used to tell spring security - which requests
to be authenticated, by which user role, at which URL request should be redirected
for authentication, validation of JWT token and etc.
    - In SecurityWebFilterChain, we use 
            .oauth2Client()
            .and()
            .oauth2ResourceServer()
- Flow with .oauth2Client()
    User hits Gateway
        ↓
    Gateway redirects to Okta login
        ↓
    User authenticates
        ↓
    Gateway receives authorization code
        ↓
    Gateway exchanges code for JWT token
        ↓
    Gateway stores token
        ↓
    TokenRelay forwards token to microservices

    - Without .oauth2Client():
        ❌ Gateway cannot participate in OAuth2 login flow
        ❌ TokenRelay filter will not work
        ❌ No access token available to forward
- Flow with .oauth2ResourceServer()
    Request with JWT
        ↓
    Gateway validates JWT
        ↓
    Extracts scopes & claims
        ↓
    Creates Authentication object
        ↓
    Security context populated

    -Without .oauth2ResourceServer():
        ❌ Validate JWT tokens
        ❌ Decode JWT
        ❌ Extract scopes/claims
        ❌ Authorize requests
        ❌ @PreAuthorize won’t work

- Bean JwtAuthenticationConverter - is used to fetch claims (includes user 
groups created in okta and etc) & add them in JWT token's authorities list,
which is used @PreAuthorize for validations. 
- Make controller method, because of below flow:
    1. User Requests API Gateway URL
    Example:
    https://your-domain/auth/login
    Request first reaches the API Gateway, controller method.

    2. API Gateway Detects User is Not Authenticated
    Because of: .oauth2Login()
    Spring Security automatically starts the OAuth2 login flow.

    Gateway redirects user to Okta authorization endpoint:
    https://integrator-9095306.okta.com/oauth2/default/v1/authorize

    3. User Logs in on Okta
    User enters:
        username
        password
    Okta authenticates the user.

    4. Okta Sends Authorization Code to API Gateway
    After successful login, Okta redirects back to:
    /login/oauth2/code/okta

    Configured using:
    redirect-uri: "{baseUrl}/login/oauth2/code/{registrationId}"

    Example redirect:
    https://your-gateway/login/oauth2/code/okta?code=abc123

    Important:
    Okta sends ONLY authorization code here, NOT JWT token yet.

    5. API Gateway Exchanges Authorization Code for Tokens
    This is where: .oauth2Client()

    helps.
    Spring Security internally calls Okta token endpoint:
    /oauth2/default/v1/token

    and sends:
        authorization code
        client-id
        client-secret

    Okta then returns:
        {
        "access_token": "eyJhbGciOiJSUzI1Ni...",
        "refresh_token": "...",
        "id_token": "...",
        "expires_in": 3600
        }
    So:
    Okta generates JWT token, API Gateway receives it

    6. Spring Security Stores Authenticated User
    Spring creates:
        OAuth2AuthorizedClient
        OidcUser
        SecurityContext

    That is why these annotations work:
    @RegisteredOAuth2AuthorizedClient OAuth2AuthorizedClient authorizedClient
    @AuthenticationPrincipal OidcUser oidcUser

    7. Controller Returns JWT Token
    Example:
    authResponse.setAccessToken(
        authorizedClient.getAccessToken().getTokenValue()
    );
    Gateway extracts JWT from Spring Security context and returns it.

    - call other services - adding JWT token in request, it should be register

FEIGN CLIENT INTERCEPTOR
- Its used, to intercept request made by interceptor & add JWT token in request
header
- Create a class for same, and should implement interface RequestInterceptor and implement 
method apply()
    @Autowired
    private OAuth2AuthorizedClientManager manager;

    @Override
    public void apply(RequestTemplate requestTemplate) {
        logger.info("UserService: Intercepting Feign client request to: " + requestTemplate.url());
        String token = manager.authorize(OAuth2AuthorizeRequest
                                        .withClientRegistrationId("my-internal-client")
                                        .principal("internal").build())
                                        .getAccessToken()
                                        .getTokenValue();
        requestTemplate.header("Authorization", "Bearer " + token);
    }


REST TEMPLATE INTERCEPTOR
- Its used, to intercept request made by interceptor & add JWT token in request
header
- Create a class for same, and should implement interface ClientHttpRequestInterceptor and implement 
method intercept()
    @Autowired
    private OAuth2AuthorizedClientManager manager;

    @Override
    public ClientHttpResponse intercept(HttpRequest request, byte[] body, ClientHttpRequestExecution execution) throws IOException {
        // Add your custom logic here (e.g., add headers, log requests, etc.)
        logger.info("UserService: Intercepting restTemplate request to: " + request.getURI());
        String token = manager.authorize(OAuth2AuthorizeRequest
                                        .withClientRegistrationId("my-internal-client")
                                        .principal("internal").build())
                                        .getAccessToken()
                                        .getTokenValue();
        request.getHeaders().add("Authorization", "Bearer " + token);
        return execution.execute(request, body);
    }


SPRING WEBFLUX
- Spring Cloud Gateway is built on Spring WebFlux, which uses a reactive non-blocking programming 
model. Therefore it requires SecurityWebFilterChain and ServerHttpSecurity & netty server 
- microservices are traditional Spring MVC applications using servlet-based architecture with 
Tomcat, so they use SecurityFilterChain and HttpSecurity.

- Spring Cloud Gateway was designed for:
    - high concurrency
    - non-blocking routing
    - efficient IO handling
    - API proxying
    - streaming
- A gateway handles thousands of simultaneous lightweight requests.
- my Sevices microservices are doing:
    - database operations
    - business logic
    - JPA/Hibernate
    - MySQL/PostgreSQL queries
- These are mostly blocking operations anyway. So standard Spring MVC is preferred.

- Main Difference
Feature	              Spring MVC	       Spring WebFlux
Server Type	           Servlet	            Reactive
Runtime	               Tomcat	            Netty
Request Model	       Blocking	            Non-blocking
Security Bean	       SecurityFilterChain	SecurityWebFilterChain
Security Annotation	   @EnableWebSecurity	@EnableWebFluxSecurity
